# Cost — المرحلة د · 10 August 2026

The free tier gives 500,000 Edge Function invocations a month. The load test
(`docs/performance/loadtest-2026-08.md`) established that latency is not the ceiling —
**quota is**. So this phase is about how many requests one visit makes, not how
fast they come back.

---

## Result

**A visit went from 28 requests to 6.** Measured the same way before and after:
a page load plus opening each of the six live games once, via Playwright against
the real backend.

| | before | after | |
|---|---:|---:|---|
| `rest:game_events` (inserts) | 21 | **2** | batched |
| `functions:get-todays-puzzle` → **400** | 3 | **0** | not asked |
| `functions:get-todays-puzzle` → 200 | 2 | 2 | cached per day |
| `functions:get-leaderboard` | 1 | 1 | 60s cache |
| `functions:get-daily-challenge` | 1 | 1 | cached per day |
| **total** | **28** | **6** | **−79%** |
| of which wasted (≥400) | 3 (11%) | **0** | |

Edge invocations specifically: **7 → 4**, and the three removed were the ones
that could only ever fail.

---

## The plan's ordering was wrong, and measurement is what said so

The plan ranked retiring `get-todays-puzzle` first and batching `game_events`
third. The measurement put `game_events` at **21 of 28 requests — 75% of
everything the site does** — while the wasted 400s were 3 of 28.

The ordering below follows the numbers instead. This is the whole reason the
phase started with a measurement rather than with the plan's table.

---

## د1 — batching `game_events` (21 → 2)

Every tracked event was its own `INSERT`. They are now queued and sent as one
bulk insert, flushed on three triggers: a 12-row threshold, a 10-second timer,
and `pagehide` / `visibilitychange`→hidden.

**The plan said `navigator.sendBeacon`. That instruction is unusable here.** The
RLS policy on `game_events` is:

```
user_id IS NULL OR user_id = (SELECT auth.uid())
```

`sendBeacon` cannot set headers. A beacon therefore arrives as `anon`, and every
signed-in player's batch would be **rejected** — the dashboard's own analytics
would quietly lose exactly the users it most wants to measure. `fetch(...,
{ keepalive: true })` survives unload *and* carries `Authorization`, which is the
actual requirement. That is what shipped.

`pagehide` matters more than it looks: rage-quits happen in the seconds before a
tab closes, so the tail of a session is the most interesting part of it.

**Verified end to end, not asserted.** A visit that produced 21 events before:

| | requests | rows in `game_events` |
|---|---:|---:|
| before | 21 | 21 |
| after | **3** | **21** |

Same data, a seventh of the requests. (Session
`285ee661-347e-4656-a10e-8ab8eded9478`, counted in the production table.)

**One false alarm worth recording.** The first check showed 13 rows, not 21 —
apparently 8 events lost. It was the harness: Playwright's `page.close()` is not
a real unload and does not fire `pagehide`. Navigating away instead produced the
full 21 in three batches (1 + 12 + 8). Worth writing down because the failure a
batching change must be checked for is *silent data loss*, and the check found
something that looked exactly like it.

**Residual exposure, stated honestly.** A hard process kill loses at most 10
seconds of queued events. Tab close, tab switch, and mobile backgrounding are all
covered. That trade was accepted rather than paid down with a shorter timer.

## د2 — not asking for what cannot be answered (3 wasted → 0)

`get-todays-puzzle` serves four game types (`ALLOWED` in its `index.ts`).
**Thirteen games call it.** The other eleven were each firing a request that
could only ever return 400 — three per measured visit.

Nothing is lost by not asking. Those games set `serverMode = false`
unconditionally; the response supplies only `serverId`, and `submitResult` opens
with `if (!sb || !puzzle_id) return null`. The board was always local.

**The function is not deprecated.** The plan proposed removing it, which would
have taken the per-game daily leaderboard («يومي») with it — `serverId` →
`submitResult` → `submit-guess` → `submissions`. `docs/operations/ai-agent-rules.md` forbids
removing features. Stopping the calls that cannot succeed achieves the saving
without the loss.

**The mirrored list is guarded by a test, because it cannot be guarded by code.**
A browser cannot read the function's Deno source at runtime, so
`tests/cost.test.js` parses both files and fails if `__served` and `ALLOWED`
diverge. Without it, drift is silent in both directions: the 400s creep back, or
a game the server now serves stops being asked.

## د3 — caches keyed by what actually changes

- **`get-todays-puzzle`** — `sessionStorage`, keyed `sura.puzzle.<game>.<date>`.
- **`get-daily-challenge`** — was cached in memory only, so a reload refetched.
  Now `sessionStorage`, keyed `sura.daily.<date>`, so it expires itself at the
  Riyadh boundary rather than on a timer. A `null` is deliberately **not**
  cached — one bad minute of network should not cost a whole day of provenance.
  This is also the endpoint the load test found at p95 2.5s under a hundred
  simultaneous opens; every request skipped is one fewer in that burst.
- **`get-leaderboard`** — a shared 60-second cache behind `__lbRows`, which is
  what makes the «عام»/«يومي» toggle and the game dropdown free to flick
  through. **Submitting busts it** (`__lbBust`), because the one moment
  staleness would be wrong is the moment a player wins and looks for their own
  new row.

## د4 — no AI call that code can replace

`groq-hint` was being called **first**, with the local deterministic hint as the
fallback. That inverts the rule («صفر نداء AI يمكن للكود أن يغني عنه»): every
hint press on a game with a registered context provider spent a Groq call even
when the local hint was already the right answer.

The order is now local first, Groq only where the local provider returns
"nothing to add" — which it signals *without* consuming a hint, so escalating
costs the player nothing and double-consumes nothing. Two side benefits: the
common hint is instant instead of waiting on a round trip that can take the full
6-second timeout, and the game behaves identically with no key, no network, and
no account.

**AI is demoted, not removed.** ✨ hints still appear where code genuinely has
nothing better.

> **Owner decision available here.** This trades a little flavour for cost: on
> supported games the first hint is now the plain 💡 deterministic one rather
> than the phrased ✨ AI one. Say the word and the order goes back — it is four
> lines in `deliverHint`.

`groq-judge` was already list-first in «زايد», and the `groq-hint` input caps
landed in the security round (A5). `groq-author`/`groq-review` are owner-driven
bot commands, not player traffic.

## Not done, and why

- **Rate limiting still isn't in the code.** The security round (A6) measured the
  in-isolate limiter as ineffective; the fix is a Cloudflare rule on
  `/functions/v1/*` and it remains an owner action. Everything above lowers
  *legitimate* traffic — none of it stops a `curl` loop.
- **`get-todays-puzzle` still writes with the service key on an unauthenticated
  call.** The exploitable parts of A2 were closed in the security round — the
  write is an idempotent upsert, `used_on` is stamped only by the caller that
  won the race, and a per-IP limit exists — and A3's solution leak is closed by
  construction (`solution` is absent from `COLS`, not merely omitted from the
  output). What remains is a design smell, not a live hole: a GET that
  materializes rows on an anonymous request. Fewer callers does not change that
  either way.

  **Correction to the audit's own wording.** A2 was written up as "any stranger
  can burn your whole bank with a `curl` loop." That was wrong. Materialization
  is keyed on `(game_type, puzzle_date)`, so the ceiling was always one bank row
  per game per day no matter how many requests arrive. The real defect in that
  code path was a concurrency bug — two simultaneous first-visitors both missed
  the cache, the loser got a null insert result and the next line dereferenced
  it into a 500 — and that is what got fixed.
