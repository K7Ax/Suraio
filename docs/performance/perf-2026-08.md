## B1 · The dictionary: from a shipped array to a built structure

`bank/words_ar.json` shipped as a JSON array of 175,627 strings, which the
client turned into a `Set`.

### First, the idea that failed

The plan said: precompute a per-board playable-word list for صندوق الحروف and
drop the dictionary entirely. **Measured: 12.1 MB raw / 3.7 MB gzip** across 78
boards — a 12-letter board matches a median of 19,244 dictionary words. That is
*eight times worse* than the file it was meant to replace. Rejected before a
line of it was written.

### What actually shipped

Three properties of the real usage decide the shape:

1. **The list is already sorted**, average word 5.2 characters, maximum 6. So
   adjacent entries share long prefixes and **front coding** (store the shared
   prefix length, then the suffix) is nearly free to apply.
2. **Nothing needs an array of 175 k JS strings.** The only operations are
   `has(w)` and one iteration in the صندوق الحروف hint. The array itself was
   ~20 MB of heap for no reason.
3. **A sorted list is binary-searchable.** 18 comparisons per query, and a query
   happens once when a player submits a word.

So: **`src/core/dict.mjs` — one packed string + an `Int32Array` of offsets +
binary search.** `bank/words_ar.txt` is generated from the JSON by
`scripts/bank/gen_dict.js` (`npm run dict`); the JSON stays as the source that Node
scripts read.

| | JSON + `Set` | front-coded + packed |
|---|---:|---:|
| gzip | 470,781 B | **201,505 B** |
| raw | 2,528,088 B | **811,771 B** |
| decode + build (median) | 24.9 ms | **18.8 ms** |
| `has()` × 2,000 | 0.10 ms | 1.30 ms |
| heap | ~20 MB | ~2.5 MB |

Lookup is 13× slower in relative terms and **0.00065 ms in absolute terms** —
below anything a human interaction can notice, paid once per submitted word, in
exchange for 269 kB and 17 MB of heap.

The class is **deliberately `Set`-compatible** — `has`, `size`,
`[Symbol.iterator]` — so `for (const w of dict)` in the صندوق الحروف hint keeps
working. This was a change of representation, not of contract.

**The correctness risk, and its guard.** Front coding assumes adjacency; binary
search assumes ordering; both assume the *same* ordering — UTF-16 code-unit
order, what `Array.sort()` gives with no comparator. If the source were ever
re-sorted with `Intl.Collator`, encoding would still work and search would
**fail silently**: no exception, no console line, just a valid word rejected on
a player who cannot see why. `tests/dict.test.js` therefore checks the ordering
of the shipped file directly, verifies `has()` against a real `Set` across the
whole dictionary, and fails if the derived file is older than its source.
`scripts/bank/gen_dict.js` additionally round-trips its own output before writing.

### Also removed: `isWord()`

A morphological matcher (up to ~500 `normalizeArabic` calls per invocation) that
**nothing called**. Round 4 deliberately stopped using it — «no morphological
invention; a letter combination that merely decomposes into affix + stem is not
an Arabic word». It had sat defined and exported ever since.

## B5 · `--charset=utf8`

esbuild defaults to `--charset=ascii`, rewriting every non-ASCII character as a
six-byte `\uXXXX` escape. Measured in an Arabic bundle: **27,367 escape
sequences = 164,202 bytes = 31.2% of `app.js` raw**.

`527,064 → 417,487 B raw (−21%)`. Gzip barely moves (−1.6%, since the escapes
compress well) — but **the parser's input shrinks by 110 kB** and the engine
stops decoding 27 thousand escape sequences on every load. The file was already
served as UTF-8. Zero risk.

Two tests hard-coded the old escaping and failed. They were made
charset-agnostic (accept either form) rather than flipped — they are about the
content being present, not its byte shape.

## B6 · Sudoku: O(81·27) per tap → O(81)

`render()` destroyed 81 nodes, created 81 replacements, and attached 81 click
listeners **on every tap** — including a tap that merely *selected* a cell.
Each render also called `conflictAt(i)` per filled cell, scanning 27 cells each:
up to **2,187 `valAt` calls per click**.

Two changes:

- **One delegated listener** on the grid; cells are built once and patched in
  place (class and text compared before writing, so unchanged cells cost
  nothing).
- **Conflicts computed with row/column/box digit counters** — two passes over
  81 cells instead of 81 × 27. Identical results.

Verified in the browser: after a click, `board.children[0] === ` the node
captured before the click, cell count still 81, selection still applied.

## B7 · Strands: same pattern

48 buttons destroyed and rebuilt per tap. Now built once per board *shape*,
patched in place, one delegated listener.

One trap worth recording: guarding a style write with
`if (cell.style.background !== bg)` never matches, because reading it back
returns the normalised `rgb(...)` form. The guard is a `data-bg` marker instead.

## B8 · نحلة: a collator per comparison → one collator, and an insert

`[...found].sort((a, b) => a.localeCompare(b, 'ar'))` asks for a collator on
**every comparison** — a full board of 22–81 words is ~500 collator
constructions per accepted word, followed by re-serialising the whole chip list
through `innerHTML`.

Now: one hoisted `Intl.Collator('ar')`, and accepting a word does a **binary
search over the rendered chips + one `insertBefore`** instead of a full re-sort
and re-render. Measured on the sort alone: 0.07 ms → 0.03 ms; the eliminated
`innerHTML` rebuild is the larger half.

## B2/B3 · Forced layout on every pointer move

Three global-ish `pointermove` paths, two reading `getBoundingClientRect()` per
event — a forced layout at up to 120 Hz, on elements GSAP was writing
transforms to in the same frame.

- **`cards.mjs`** read the rect of each card per event. Worse than the cost: the
  hover lift (`y`, `scale`) *changes the rect being read*, so the tilt was
  computed against geometry moving underneath it. Now cached on `pointerenter`,
  invalidated by a shared scroll/resize epoch — two listeners for the whole
  module.
- **`loom.mjs`** read the stage rect per event and then scanned ~11,900 cells
  (`Math.hypot` + `Math.random` each) to unweave threads — **while the cloth was
  hidden behind the film on the home route**, which is what `index.html` ships.
  Added `setInteractive()`, called from `applyRoute`: the hand is lifted
  wherever the cloth is not visible. The cloth itself is never torn down, so
  route changes stay a crossfade.

Verified: on home, `window.__sura.loom.interactive === false` with
`data-backdrop="video"`.

## Three small ones

- `buildPicker()` called `unlocked(game, i)` inside a 21-iteration loop; each
  call re-read `frontier()` **and** `mask()` — **42 synchronous
  `localStorage.getItem` + `JSON.parse` per picker open**. Both hoisted.
- Leaderboard search ran `querySelectorAll` over the table plus a
  `querySelector` and `textContent` read **per row, per keystroke**, undebounced.
  Now indexed once, invalidated by a `MutationObserver` on the rows container,
  and debounced 120 ms.
- `bank/words_ar.json` was downloading serially after supabase-js. Added
  `<link rel="preload" as="script">` for `app.js` so it downloads in parallel
  with the CDN fetch. **Deliberately not `defer`**: `defer` would move `app.js`
  execution *after* the inline navbar-glue script that currently follows it,
  which is a behaviour change. A preload is not.

## Measured and rejected

Recording these so the round is not repeated.

**B9 — a runtime prefix index for the صندوق الحروف hint.** The linear scan costs
**4.0 ms**; building the per-board index costs **9.5 ms**. The index only pays
for itself after three hint presses in one round, which is not the common case.
And B1 already removed the reason it looked expensive. **Not built.**

**B4 — deferring the loom's initial build.** The build really does issue ~22,000
`fillRect` calls and allocate ~56 MB of canvas before first interaction. But
deferring it would leave the first frame empty: the loom is *deliberately* what
paints immediately so the video can dissolve in over it, rather than the visitor
seeing a blank screen while the CDN responds. Its *repeat* cost is already
avoided — `applyRoute` skips `reweave` whenever the backdrop is video. **The
one-time cost is a design decision, and it stays.**

**B10's second half — dynamic imports for the four soft-hidden games.**
`zayid` (33 kB), `missing_word` (19 kB), `story_order` (16 kB) and `tiles`
(11 kB) are bundled but unreachable. That is ~79 kB of source, perhaps ~20 kB
gzipped, against a 137.5 kB bundle. Splitting them means reworking the game
registry and its initialisation order for a gain **one thirteenth the size of
the dictionary win**, with meaningfully more risk. **Deferred, not refused** —
worth doing if the bundle grows.
