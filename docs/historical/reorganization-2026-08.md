# Repository reorganization — August 2026

A structural reorganization of the Sura workspace. **No runtime behaviour, UI,
game logic, API, Supabase behaviour, or security control was changed.** The
deployed artefact is byte-accounted against a pre-reorganization snapshot in §8.

## 10. Critical assessment

**If a senior engineer joined today, what would still confuse them?**

1. **Two SQL directories remain two directories.** `supabase/sql/README.md` now
   explains the split and marks each file *applied / check first / never run*,
   but the honest state is that **schema history lives partly in an ordered
   ledger and partly in a folder of hand-pasted scripts with no global order.**
   There is no way to reconstruct "what is in production" from the repo alone.
   The migrations were applied by hand through the SQL Editor, and
   `supabase db push` is banned by owner policy. Documentation mitigates this;
   it does not fix it. **This is the largest remaining structural weakness.**

2. **`app.js` is a committed 441 KB build artefact.** CI enforces that it
   matches `src/`, but every `src/` change produces a large binary-looking diff,
   and the first instinct on seeing a bug in `app.js` is to edit it. `.gitattributes`
   now marks it `linguist-generated -diff`, which helps reviewers and does
   nothing for the person who opens it in an editor.

3. **The test suite reads source files and asserts on their text.** This is
   deliberate and `tests/README.md` argues the case — five layers, no shared
   compiler, and the characteristic bug is one copy drifting from another. But
   it means renaming a CSS class can fail a test in a file that looks unrelated,
   and a newcomer will read that as flakiness before they read it as design.

4. **Nothing tests the app end to end through a browser with a real session.**
   `sweep.js` plays 126 rounds and the route check catches load errors, but no
   automated test signs in, because signing in requires entering a password,
   which this agent will not do. **Auth is the least-covered critical path in
   the product**, and archiving the old Python harnesses did not close that gap —
   it only stopped pretending those files were the test suite.

5. **The repository has 13 tracked files and ~403 to be committed.** Until the
   owner runs the baseline commit, `git log` tells a newcomer almost nothing,
   `git blame` is useless, and none of this structure is defended by history.
   **This is the single highest-value remaining action**, and it is the owner's
   to take — see `docs/operations/git-hygiene.md`.

6. **`promo/` is 81 MB and 111 files** for a 20-second launch film, sitting
   beside the product at the same level of the tree. It is correctly isolated
   and correctly gitignored where it matters, but its prominence overstates its
   importance relative to `src/`.

What a newcomer would now get right quickly: what ships and what does not (the
`dist.js` whitelist), where to change a game, why `_headers` must not be edited,
which SQL file will break production if run, and why the camel cursor is a PNG
in `public/brand/` and not the 2 MB master in `_design-src/`.
